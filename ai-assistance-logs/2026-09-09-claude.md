## 2. LLM response

Yes. The feature you want is **KV cache (prompt cache) saving**. Your "save point" is the model's key-value attention cache after processing the context prompt.

### The core technique

When a model processes your long prompt, it computes a KV cache — the internal attention state for every token. Normally this is discarded between sessions. You can serialize it to disk once, then reload it instantly on subsequent runs, skipping the reprocessing (prefill) of the shared prefix entirely.

### Concrete tooling

**llama.cpp** (best fit — supports Gemma, Llama, and Phi as GGUF):
- The `llama-cli` / server has **slot save/restore**. Save state with the `--slot-save-path` option plus the server's `/slots/{id}?action=save` endpoint, then `action=restore`.
- At the CLI level, `--prompt-cache <file>` writes the state to a file, and `--prompt-cache-ro` reuses it read-only. This is essentially exactly your save-point idea.
- Programmatically, the API calls are `llama_state_get_data` / `llama_state_set_data` (and the `_seq_` variants to save just one sequence's cache).

**Ollama** (simpler to deploy):
- It keeps prompts cached in memory while the model is loaded and reuses the shared prefix automatically, but does **not** persist the cache to disk across restarts as cleanly. Set `OLLAMA_KEEP_ALIVE=-1` to hold the model and cache resident indefinitely — good for an always-on kiosk laptop, less good if it fully powers down.

### Important caveats for your off-grid setting

The saved cache is **tightly coupled** to: the exact model file/quantization, the exact prompt tokens, and often the llama.cpp build and context settings. Change any of these and the cache is invalid. Lock your versions before deploying.

Cache files can be **large** (hundreds of MB to several GB depending on context length and model). On solar-powered laptops with limited storage, check the size tradeoff — but reloading from disk is still far cheaper in **power and time** than recomputing prefill, which is the real win for you.

Given the power constraints, I'd lean toward **llama.cpp with `--prompt-cache`** written once at provisioning time and shipped read-only on each laptop, rather than recomputing per boot.

One thing worth confirming before you build around this: what's your usage pattern per laptop — does it stay powered on between users (favoring keep-alive in memory), or fully shut down between sessions (favoring on-disk prompt cache)?

### Step 1: Build the save point (run once, at provisioning)

```python
# build_savepoint.py
from llama_cpp import Llama
import pickle

MODEL_PATH = "model.gguf"
CONTEXT_PROMPT = open("context_prompt.txt").read()

llm = Llama(
    model_path=MODEL_PATH,
    n_ctx=8192,        # must be large enough for prompt + conversation
    n_gpu_layers=0,    # 0 = CPU only; adjust if the laptops have a usable GPU
    verbose=False,
)

# Process the long context prompt once (this is the slow prefill step)
llm.eval(llm.tokenize(CONTEXT_PROMPT.encode("utf-8")))

# Capture the "save point"
state = llm.save_state()
with open("savepoint.pkl", "wb") as f:
    pickle.dump(state, f)

print("Save point written.")
```

### Step 2: The interactive program (run each session)

```python
# chat.py

import pickle

MODEL_PATH = "model.gguf"

llm = Llama(
    model_path=MODEL_PATH,
    n_ctx=8192,        # MUST match the value used in build_savepoint.py
    n_gpu_layers=0,
```

## 11. User request

Let's say that CONTEXT_PROMPT is read from a single markdown file. Is there a way to measure whether the markdown file is so long that it exceeds the sliding context window?

## 12. LLM response

Yes. You measure it by **tokenizing** the markdown and comparing the token count against your `n_ctx`. Two things to clear up first, though, because "sliding context window" is doing some tricky work in your question.

### Two different limits, don't conflate them

**`n_ctx`** — the context size *you* set when loading the model. This is the hard limit that matters for your save-point. If your prompt's token count exceeds `n_ctx`, tokens get dropped (or the call errors), and your save-point is corrupt/incomplete. This is the one to check against.

**The 512-token sliding window** in Gemma 4's architecture is *not* a limit on how much text the model can take in. It's an internal attention mechanism — most layers attend only to a local 512-token neighborhood, but the model interleaves periodic **global** attention layers (the spec says the final layer is always global) so information still propagates across the whole context. So a prompt longer than 512 tokens is completely fine and normal; the model still "sees" all of it. You do **not** need to keep your prompt under 512 tokens. The real ceiling is the model's trained context length (128K for E4B) and, more immediately, whatever `n_ctx` you chose.

So the thing to measure against is `n_ctx`, not the sliding window.

### How to measure

Tokenize with the actual model so the count is exact (character or word counts are unreliable — Gemma's tokenizer splits unpredictably):

```python
from llama_cpp import Llama

MODEL_PATH = "gemma-4-E4B-it-UD-Q4_K_XL.gguf"
N_CTX = 8192
RESERVE_FOR_CHAT = 2048   # room for the conversation on top of the loaded context

llm = Llama(model_path=MODEL_PATH, n_ctx=N_CTX, n_gpu_layers=0, verbose=False)

text = open("context_prompt.md", encoding="utf-8").read()
tokens = llm.tokenize(text.encode("utf-8"))
n = len(tokens)

budget = N_CTX - RESERVE_FOR_CHAT
print(f"Context prompt: {n} tokens")
print(f"n_ctx: {N_CTX}, usable after reserve: {budget}")

if n > N_CTX:
    print("❌ EXCEEDS n_ctx — prompt will be truncated. Raise n_ctx or shorten the prompt.")
elif n > budget:
    print(f"⚠️  Fits in n_ctx but leaves only {N_CTX - n} tokens for the actual conversation.")
else:
    print(f"✓ OK — {budget - n} tokens free for conversation.")
```

### Why the reserve matters for your design

This is the part specific to your save-point setup. The save-point captures the KV cache after the context prompt. Every user turn afterward *adds* tokens on top of that. So you don't just need `prompt ≤ n_ctx` — you need `prompt + longest expected conversation ≤ n_ctx`. That's what `RESERVE_FOR_CHAT` models. If the prompt fills 7,900 of 8,192 tokens, the conversation dies almost immediately.

If your markdown is genuinely large, either raise `n_ctx` (costs memory and slows prefill — fine on the 64 GB i7, watch it on the 16 GB i5) or trim the markdown. Given both machines are CPU-only, a smaller `n_ctx` also means a faster one-time prefill when you build the save-point, so don't set it larger than you need.

### `n_ctx` is a runtime setting, not a build-time one

The willingness to let the build take a long time doesn't actually buy you a larger `n_ctx`. Here's why:

`n_ctx` fixes the size of the KV cache — a block of memory that must be allocated **every time the model loads**, on every laptop, every session. It's not something you "bake in" once during a slow build and then get for free later. The save-point you capture is sized to that `n_ctx`, and the runtime script must load with the *same* `n_ctx` to restore it. What the long build *does* buy you is tolerance for slow **prefill** (processing the prompt tokens). That's real and useful — it means you don't care how long the one-time context ingestion takes. But prefill time and `n_ctx` are different axes. So the constraint on `n_ctx` remains runtime RAM on the i5, unaffected by build patience.

### What actually sets the ceiling

`n_ctx` needs to satisfy: **context prompt tokens + longest expected conversation ≤ n_ctx**, while the KV cache still fits comfortably in the i5's 16 GB alongside the ~5 GB model.

Gemma 4 E4B's hybrid attention (mostly 512-token local windows with periodic global layers) keeps its KV cache smaller per token than a fully-global model, so you have room. This is where the hybrid attention matters.
